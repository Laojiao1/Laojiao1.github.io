LRU cache

4. C++ LRU cache

引入

为什么 AI 引擎需要 Cache？

在深度学习编译框架（比如 TVM）中，编译一个特定的 GPU 算子（比如“128x128 的半精度矩阵乘法”）非常耗时。

为了加速，一旦某个算子被编译好，我们就想把它存进缓存里。下次碰到一样的算子，直接拿编译好的机器码就行。

问题来了：机器的内存是有限的（假设最多只能存 1000 个算子）。如果缓存满了，而又来了一个新算子，我们该把谁踢出去？

最合理的逻辑是：把**“最近最少使用（Least Recently Used, LRU）”**的那个老算子踢掉，因为将来再用到它的概率最低。

单一数据结构的致命缺陷

如果让你来实现这个缓存，并且要求：查找数据、插入数据、剔除老数据，这三个操作的时间复杂度都必须是绝对的 O(1)，你会怎么选数据结构？

  1. 纯数组/队列（std::vector / std::queue）：
    • 淘汰老数据很简单（踢掉尾部）。但查找一个算子在不在里面，必须从头遍历，时间复杂度是 O(N)！太慢了！
  2. 纯哈希表（std::unordered_map）：
    • 查找数据是神级的 O(1)！但是，哈希表内部是无序的，它根本没有“时间顺序”的概念。你根本不知道哪一条数据是很久以前放进去的。

哈希表 + 双向链表

为了达到三个 O(1) 的苛刻要求，大神们把两种数据结构强行缝合在了一起：

std::unordered_map（负责 O(1) 定位） + std::list（双向链表，负责 O(1) 维护时间顺序）。

这是整个算法的核心：

  1. 双向链表：里面存着真正的数据包 [Key, Value]。
    • 规矩：谁只要被访问了（无论是刚存进去，还是被查阅了一次），谁就立刻被强行拉到链表的最头部（头部 = 最新）
    • 那么随着时间流逝，链表的最尾部，自然就是那个“最近最少使用”的算子。一旦超载，直接把尾巴切掉，O(1) 搞定淘汰！
  2. 哈希表：
    • Key 是算子的名字。
    • Value 不是真实的数据，而是指向双向链表里那个节点的指针（迭代器 std::list::iterator）！
    • 有了它，我们找数据时再也不用遍历链表了。哈希表 O(1) 瞬间告诉你该节点在链表里的精确位置；拿到位置后，链表 O(1) 瞬间把这个节点剪切、并粘到头部去更新时间。

这就是 LRU 的底层物理架构。

  • 根据题目条件，直接用数组 hash_map[10005] 模拟哈希表，避免 unordered_map 的哈希冲突和内存碎片化问题

  • 采用一个自己指向自己的 dummy 空节点，把直线型链表接成一个首尾相连的“循环双向链表”。这样dummy->next 永远都是最新的节点，dummy->prev 永远都是最旧的节点

  • 当缓存写满需要淘汰老数据时，不使用 delete 销毁旧节点，只需要直接摘下最尾部即将被淘汰的节点，擦除旧数据、换上新 Key 和 Value，然后重新挂到链表头部继续使用。

  • 不采用 list ，自己定义一个 node 结构体，直接手写静态双向链表

    • 底层逻辑：std::list 的每次 emplace_front 都会在堆（Heap）上调用操作系统的 new 申请内存。堆内存碎片化严重，导致节点散落在内存各处，CPU Cache 命中率惨不忍睹。

  • 在构造函数中抛弃高级语言的 for 循环，改用底层的 memset 清空哈希表数组；同时利用 IO 切断 C++ 流同步。

面试题

为什么 LRU 必须是“哈希表 + 双向链表”的组合？用单向链表或者数组不行吗？

底层动机：考察对数据结构时间复杂度的绝对掌控。

参考回答：

  • 为什么不用数组？ 数组虽然查找是 O(1)，但如果遇到数据淘汰（移出旧元素并移动后续元素）或者更新新鲜度（移到头部），时间复杂度会立刻暴增到 O(N)。
  • 为什么不用单向链表？ 在触发缓存命中时，我们需要把当前的节点从链表中间“抠出来”移动到头部。在单向链表中，要删除一个节点，必须知道它的前驱节点。如果不从头遍历，我们就找不到前驱节点，这让操作再次退化成 O(N)。
  • 只有双向链表：自带 prev 和 next 指针，只要通过哈希表在 O(1) 内锁定了它的位置，就能在 O(1) 内完成它的剪切和插入。

在双向链表里，为什么节点必须存 std::pair<Key, Value>？只存 Value 会发生什么灾难？

底层动机：考察数据结构闭环与反向追踪能力。这也是最多人死在白板手写阶段的一个坑。

参考回答：

存 Key 的唯一目的是为了应对**“驱逐残留（Eviction）”**。

当缓存容量达到上限时，我们必须淘汰链表最尾部的节点。如果节点里只存了 Value，我们确实可以轻易地把这个尾部节点从链表里删掉。

但是，哈希表里还残留着指向这个节点的“幽灵记录”！

因为哈希表的删除函数 erase() 必须传入 Key 才能起效。如果链表节点里没有反向记录这个 Key，我们将永远无法清理哈希表，最终导致系统内存泄漏和逻辑彻底错乱。

在把命中节点移动到头部时，你用的是 std::list::splice，如果改成先 erase 删除节点，再 push_front 插入节点，会有什么隐患？

底层动机：考察对 C++ 内存分配开销和迭代器失效（Iterator Invalidation）的深刻认知。

参考回答：

有两个极大的隐患：

  1. 性能开销（致命）：erase 会触发节点对象的析构和堆内存回收，push_front 会触发底层 new 去重新申请堆内存。频繁的内存分配与释放是极高昂的系统调用开销。而 splice 仅仅是改变了几个指针的指向，真正的物理内存完全没动。
  2. 迭代器失效：如果用 erase，原来存在哈希表中的那个迭代器就瞬间失效（变为了悬垂指针），后续再访问必死无疑。而 splice 保证了被移动的节点，其迭代器永远有效，无需同步更新哈希表。

你手写的这个 LRU Cache 是线程安全的吗？如果不安全，在深度学习框架的多线程环境下该怎么改造？

底层动机：将 LRU 与上一节课的 Thread Pool 进行系统级联动。

参考回答：

**绝对不安全。**标准库的 std::list 和 std::unordered_map 都不具备并发保护。

如果将其应用在多线程高并发的算子调度中，多个线程同时读写哈希表会导致严重的 Data Race，甚至使红黑树/哈希桶结构彻底撕裂。

改造方案：最简单的方案是在类内部加一把全局 std::mutex，在 get 和 put 的最开头上锁。

但在工业级（如 Redis 底层或 AI 引擎）缓存中，由于“读操作（Get）”远多于“写操作（Put）”，全局锁会成为巨大瓶颈。应当采用 std::shared_mutex（读写锁），或者采用**分段锁（Segmented Lock）**将哈希表拆分成多个桶，以此将并发粒度降到最低。
